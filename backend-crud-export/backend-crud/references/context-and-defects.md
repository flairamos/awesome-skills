# 上下文纪律、缺陷与注释

## 一、上下文里保留什么

长期保留的只有**业务卡片**：

- 模块名与一句话目标
- 实体及关键字段的**业务含义**
- 主流程与状态流转
- 接口清单（方法 + 路径 + 用途）
- 角色与权限
- 外部依赖、事务/一致性要求
- 待确认问题与已确认的决定

不保留：

- 代码片段、完整文件内容、diff
- 结构体类型、tag、函数签名等实现细节
- 堆栈、日志、测试输出、SQL 执行计划
- 缺陷的详细描述（只在上报时出现）
- 临时调试结论、被否决的方案
- 用户的原始长需求全文（压缩成卡片即可）

判断标准：**下一个接手的人只看这张卡，能否理解业务；要改代码时，是否必须重新打开文件。** 如果是，说明卡是对的。

现实约束：已经读入对话的内容无法物理删除。这里约束的是"不复制、不写入记录、不在摘要和交付里复述"，让后续上下文只围绕业务推进。

## 二、压缩时机

在这些节点重写业务卡片，而不是累积聊天记录：

1. 侦察完成、开始设计接口时
2. 每个模块的代码生成完成时
3. 缺陷修复完成时（只更新业务结论，不留缺陷细节）
4. 会话被压缩或恢复时

压缩后，旧的实现细节不再引用；需要时按路径重新读文件。不要凭记忆描述某段代码"应该是这样"。

## 三、缺陷上报

### 分级

| 级别 | 判定 | 例子 |
| --- | --- | --- |
| P0 | 会造成数据丢失、越权、注入、严重不一致、线上事故 | 无 WHERE 删改、租户条件缺失、SQL 拼接、事务缺失、密钥泄露、请求路径 panic、并发竞态、未确认的破坏性接口变更 |
| P1 | 当前不一定出事，但迟早出问题 | 缺参数校验、列表无上限、错误被吞、错误码不统一、明显 N+1、无超时、软删除与唯一索引冲突 |
| P2 | 可读性与风格 | 命名、重复代码、过长函数 |

只报 P0/P1；P2 用户问再说。不要把所有 lint 提示都升级成"严重缺陷"。

### 上报格式

一条一行，最多两行：

```
P0 · internal/order/repo.go:88 — 影响：按 ID 更新未带 tenant_id，可跨租户改单。修法：条件补 tenant_id 并加测试。现在修吗？
```

P0 发现即报，不等步骤结束；P1 在当前步骤结束前汇总，最多 3 条。给建议时不说套话，不写"建议优化一下"，直接说改什么、代价是什么。

### 不记录

- 不把缺陷写进业务卡片、设计文档、Postman 描述。
- 不在下一次回复重复已报过的缺陷，除非用户问或问题复发。
- 修复后只确认结果，不归档"曾经有个 bug"。
- 不贴完整堆栈、不贴整段错误代码；需要定位时给 `path:line` 和关键一行。

## 四、什么时候必须问

出现下列情况立即停下来问，不要猜：

- model 缺字段，但接口需要；或字段业务含义不明
- 删除是软删还是硬删、是否需要保留历史
- 状态枚举与流转规则不完整
- 权限/租户边界不清，或涉及跨角色操作
- 需要改表、回填数据、加索引、改接口契约
- 需要引入新依赖、新中间件、新外部服务
- 需求与现有代码行为冲突
- 要执行破坏性 SQL 或迁移

提问格式：一次最多 3 个；每个给 A/B 候选和后果；能给推荐就给推荐。不要用开放式长问题。

## 五、注释规则

默认不写注释。只在以下位置写 1–2 行，解释**为什么**：

- 并发控制、锁顺序、幂等键的选择
- 事务边界为何这样划
- 不直观的业务规则（如"退款金额不含运费"）
- 必要的 workaround 及其原因、移除条件
- 复杂查询/索引选择的原因

不要写：

- 复述函数名或代码行为的注释（`// 获取用户`）
- 分隔线、装饰性注释
- 注释掉的旧代码
- 每个字段/每个分支都来一行
- 过期 TODO；需要跟踪就写进待确认问题

项目 lint 强制要求导出符号注释时，按项目规范保留最短形式；没有强制就不加。

示例：

```go
// 先锁订单再扣库存，保证并发取消与支付回调不会交叉扣减。
```

```go
// 这里不能用事务：第三方回调必须在本地落库前完成签名校验，
// 否则重试会重复占用连接。校验失败直接返回，不写库。
```

## 六、SQL 守卫

执行前：

```bash
node scripts/sql-guard.mjs --sql "DELETE FROM orders WHERE id = ?"
node scripts/sql-guard.mjs --file migrations/20261022_cleanup.sql
node scripts/sql-guard.mjs --scan .
```

- `0`：未发现无条件删改或破坏性 DDL
- `1`：存在危险语句，禁止执行
- `2`：参数/路径错误

被拦截时，不要改写 SQL 绕过（例如把 `DELETE FROM t` 拆成 `DELETE FROM t WHERE 1=1`），先向用户说明并给安全方案：补主键/租户条件、先 SELECT COUNT 评估、分批 + LIMIT、软删除、备份后手工执行。

守卫覆盖普通 DML/DDL，不解析存储过程/触发器内部逻辑；这类对象要人工复核。
